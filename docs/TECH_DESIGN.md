# zpl-rest 打印服务平台 技术方案

版本：v1.0（已确认）
日期：2026-10-25（v0.1 初稿；2026-10-25 确认修订）
状态：已确认，进入开发

## 一、需求总览

在现有 zpl-rest 服务基础上升级为工厂打印服务平台。原始需求共 5 个工作流程（原描述中两条编号均为"第三"，按内容拆分）：

1. 打印机设置——自动发现 Zebra 打印机，一键添加；找不到时手动添加；按型号自动匹配打印设置
2. 标签模板设置——可视化编辑；模板自动生成 JSON 文件；按 JSON 生成批量打印用的 xlsx 表格文件，上传即可生成打印队列
3. 打印机与标签模板绑定——每台打印机对应一个默认模板，减少换纸/换碳带频率；允许手动修改
4. 打印队列——查看打印机状态；通过队列批量打印（上传 xlsx 生成队列）；支持预览、断点续传、打印机状态返回
5. MCP 服务器——将打印能力封装为 MCP 服务，供 AI 调用

## 二、现有系统基线

- 技术栈：Node.js 22 + Express，REST 端口 8000，WebSocket 端口 8001，diskdb JSON 文件存储
- 已完成改造：本地 ZPL 预览渲染（zpl-renderer-js，Zebrash WASM）；label 宽高单位统一为 mm；ZT510 直接热敏模板参数（^MTD/^MD15/^PR2）已验证
- 保留能力：占位符替换（${var} 与 Mustache）、打印任务历史、重打、Web UI

兼容原则：现有 REST 接口保持向后兼容，新能力以新增接口为主。

## 三、工作流程一：打印机自动发现与添加

### 3.1 功能要求

- 自动发现网段内的 Zebra 打印机，列表展示，一键添加
- 发现失败时支持手动添加（保留现有表单，增加型号选择）
- 添加时根据打印机型号自动匹配最合适的打印设置

### 3.2 技术方案

发现采用两步策略：

第一步，网段扫描。用户指定网段（默认取服务器所在网段，如 192.168.8.0/24），并发探测各地址的 TCP 9100 端口（并发 64，超时 500ms，总耗时约 2~5 秒）。

第二步，设备识别。对 9100 端口连通的设备发送 ZPL SGD 查询：

- 设备型号：`! U1 getvar "device.product_name"`)
- 打印头分辨率：`! U1 getvar "device.head.resolution.in_dpi"`
- 链路兼容性：`! U1 getvar "comm"`（确认为 Zebra 设备，非打印机返回判定为噪音）

按 DPI 换算密度（203dpi→6dpmm，300dpi→8dpmm），生成发现结果列表（IP、型号、DPI、在线状态），前端勾选后一键入库。

### 3.3 型号匹配打印设置

内置"型号 → 推荐设置"映射表（存于 lib/printer_profiles.js，可扩充）：

- 密度（由 DPI 换算）
- 介质类型默认值（热敏/热转印，ZT510 直接热敏场景固化为 ^MTD + ^MD15 + ^PR2，来自实测）
- 默认打印速度
- 标签纸宽高上限（用于模板编辑器的边界校验）

映射表未覆盖的型号：按 DPI 推导密度，其余留空由用户补填。

### 3.4 新增接口

- POST /rest/discover {subnet} —— 执行网段扫描，返回发现列表
- 现有 POST /rest/printer 增加 device_model 字段与推荐设置自动带入

## 四、工作流程二：可视化标签模板与 JSON

### 4.1 功能要求

- 模板以可视化方式设置（拖拽排版，所见即所得）
- 模板持久化为 JSON 文件
- 按模板 JSON 自动生成批量打印用的 xlsx 表头文件；用户填写数据后上传即生成打印队列（队列细节见工作流程四）

### 4.2 模板 JSON 结构（由设置动态生成）

JSON 采用"固定骨架 + 动态内容"模型：顶层骨架固定，一切具体内容均来自用户在编辑器中的设置——添加了什么元素、每个元素设置了什么属性，JSON 就保存什么。不预设死的元素清单。

{
  "name": "收货标签",
  "size": { "width_mm": 84.8, "height_mm": 23.8 },
  "print_settings": {
    "dpmm": 8,
    "mode_direct_thermal": true,
    "darkness_offset": 15,
    "speed_ips": 2
  },
  "elements": [
    { "type": "text", "id": "el_01", "x_mm": 6.25, "y_mm": 3.75,
      "props": { "size_mm": 7.5, "bold": false,
                 "content": "收货单：${order_no}" } },
    { "type": "barcode", "id": "el_02", "x_mm": 6.25, "y_mm": 12,
      "props": { "symbology": "code128", "height_mm": 9,
                 "content": "${barcode}" } }
  ],
  "variables": ["order_no", "barcode"]
}

设计要点：

- 骨架：name、size、elements、variables 四个顶层键固定不变，保证编译器、xlsx 生成器、MCP 等下游模块的解析稳定
- elements 数组：每个元素由 type、id、位置（x_mm/y_mm）和 props 组成；props 内的属性完全由该元素在编辑器属性面板中的设置决定，设置什么存什么，未设置的属性不落盘、编译时用默认值
- 元素属性注册表（lib/element_registry.js）：每种元素类型登记"可设置属性清单 + 默认值 + 对应 ZPL 指令"，编辑器据此动态渲染属性面板，编译器据此生成 ZPL。新增元素类型或属性只需扩展注册表，JSON 结构与编译器骨架不动
- print_settings：模板级打印设置，新建模板时从所选打印机型号的推荐设置（工作流程一的 printer_profiles）自动带入，可按模板覆盖；编译时输出 ^MTD/^MD/^PR 等指令，替代手写
- variables：编辑器扫描所有元素 props 中的 ${var} 占位符自动收集，作为 xlsx 表头生成依据，无需手动维护
- 兼容存量模板：数据库中已存的手写 ZPL 模板标记为 zpl_raw 类型，继续走原逻辑；可视化模板标记为 visual 类型
- 反向解析：对 visual 模板支持 JSON↔编辑器双向；对手写 zpl_raw 仅预览不反解（避免解析错误破坏原模板）

### 4.3 可视化编辑器

- 前端画布按 mm 网格渲染（1mm = N 像素随缩放），元素拖拽定位、属性面板改字号/内容/条码类型
- 实时预览：每次修改后将"JSON 编译出的 ZPL"送现有本地预览接口出图
- 编译器（lib/zpl_compiler.js）：JSON → ZPL，按打印机 dpmm 将 mm 换算为点；预览用默认 8dpmm，打印时按目标打印机实际 dpmm 编译

### 4.4 xlsx 生成与上传

- 下载接口：GET /rest/label/:id/xlsx-template —— 按模板 variables 生成表头（列名 = 变量名），附一行示例数据
- 上传即入队：见工作流程四

### 4.5 新增接口

- POST /rest/label/visual —— 新建/更新可视化模板（JSON）
- GET /rest/label/:id/xlsx-template —— 下载批量打印 xlsx 模板

## 五、工作流程三：打印机与模板绑定

### 5.1 功能要求

每台打印机绑定一个默认标签模板，打印请求可省略模板参数，减少换纸/换碳带频率；绑定可手动修改。

### 5.2 技术方案

- printer 记录新增字段：default_label_id（绑定的模板 id）、media_note（介质备注，可选）
- 打印接口兼容：POST /rest/print 中 label 参数变为可选；缺省时取打印机的 default_label_id，两者都无则报 400
- 打印机页面增加绑定下拉框；发现/手动添加流程完成后可直接引导绑定
- xlsx 批量打印按"列名 printer 指定打印机"或"整表指定一台打印机"两种模式，均使用该打印机的绑定模板（详见 4.4/6.4）

## 六、工作流程四：打印队列

### 6.1 功能要求

- 队列查看与管理（当前任务、进度、失败项）
- 上传模板对应的 xlsx 批量入队
- 打印前支持预览
- 断点续传：服务重启或打印中断后可从断点继续
- 打印机状态返回（缺纸、暂停、打印头开启等）

### 6.2 队列数据模型

新增 queue 集合（diskdb）：

{
  "queue_id": "...",
  "printer_id": "...",
  "label_id": "...",
  "source": "xlsx:文件名",
  "total": 500, "done": 123, "failed": 2,
  "status": "running | paused | done | failed_partial",
  "items": [
    { "seq": 1, "data": {...}, "state": "done | failed | pending", "error": "" }
  ]
}

### 6.3 执行机制

- 队列执行器逐条发送，每条落盘后更新状态（天然支持断点续传：服务重启后扫描 status 为 running/paused 的队列，从第一个 pending 续打）
- 速率控制：相邻任务间隔可配（默认 200ms），避免 ZT510 缓冲区溢出
- 失败处理：单条失败记录原因，可整队重打失败项
- 前端：队列页展示进度条、暂停/继续/终止按钮、失败清单导出（xlsx）

### 6.4 xlsx 批量打印

- 上传接口：POST /rest/queue/upload（multipart），参数 queue 文件 + printer（或表格内 printer 列指定多打印机）
- 解析校验：列名与模板 variables 匹配校验，缺失列/空值在入队时标记警告，不入队异常行
- 预览：入队前用第一行数据渲染本地预览图确认版式，确认后开始打印
- 断点续传确认策略：服务重启后队列自动暂停，前端提示"继续/放弃"（避免误重打）

### 6.5 打印机状态监控

- 状态采集：定期（默认 10 秒，可配）向每台在线打印机发送 ZPL `~HS` 指令，解析返回的状态字段（缺纸、色带/打印头打开、暂停、缓冲区）
- 推送：状态变化经现有 WebSocket（8001）广播到前端
- 队列联动：打印机缺纸/开盖时队列自动暂停，状态恢复后提示继续
- ZT510 注意：~HS 需在打印任务间发送，执行器在每条任务前后检查一次状态

## 七、工作流程五：MCP 服务器

### 7.1 功能要求

将平台能力封装为 MCP 服务，供 AI（如 WorkBuddy、Claude 等）调用。

### 7.2 技术方案

- 实现：@modelcontextprotocol/sdk（官方 Node SDK），以 streamable HTTP 方式运行在独立端口（默认 8002），同进程挂载
- 工具清单：
  - list_printers —— 列出打印机及状态
  - list_labels —— 列出标签模板
  - print_label —— 单张打印（参数 printer、label、data）
  - create_queue_from_xlsx —— 从上传的 xlsx 创建批量打印队列（AI 侧传入文件路径或 base64）
  - get_queue_status / control_queue —— 查询/控制队列（暂停、继续）
  - preview_label —— 返回标签预览图
- 安全：token 鉴权（config.json 配置 mcp_token），避免局域网裸奔

## 八、实施阶段

按依赖关系分四期，每期独立可验收：

- 阶段 1：打印机自动发现 + 手动添加增强（型号库与推荐设置）
- 阶段 2：可视化模板编辑器 + JSON 模型 + 编译器 + xlsx 表头下载
- 阶段 3：打印队列（xlsx 上传、预览、断点续传、状态监控、WebSocket 推送）
- 阶段 4：MCP 服务器

阶段 1、2 相对独立可并行；阶段 3 依赖阶段 2 的模板 JSON；阶段 4 依赖前三个阶段的接口稳定。

## 九、已确认决策（2026-10-25 用户逐条确认）

1. 自动发现：同局域网内查找，扫描服务所在服务器的本机网段；服务部署在指定服务器上
2. xlsx 规则：列名对应标签模板变量；支持表格内指定列（printer 列）实现多打印机分发
3. 打印队列：按时间排序显示；可删除队列；出现打印机故障、缺料等情况时暂停，可断点续打
4. 可视化编辑器：操作尽量简单，元素内容尽量全（首期覆盖文本、Code128、QR、矩形框、横线，注册表机制便于后续扩展）
5. 打印机状态轮询间隔 10 秒：确认
6. MCP：局域网 HTTP 方式（端口 8002），供局域网内 AI 调用，保留 token 鉴权
7. 部署形态：测试期 Node 直跑；后续支持 Docker 部署与 exe 程序打包（技术选型已规避原生编译依赖，ZPL 渲染为 WASM、xlsx 处理为纯 JS，满足打包要求）
